# Roadmap 2026–2031

## Roadmap philosophy

This roadmap is capability-gated, not date-promised. Each stage advances only after measurable invariants are satisfied.

Arcana should not publish an execution protocol before its internal abstractions survive real use. It should not pursue ecosystem scale before the SDK is usable. It should not pursue autonomy breadth before recovery, verification, and enforcement are reliable.

## 2026 — Governed execution foundation

### Objective

Finish the deterministic governance kernel and make every consequential action observable and enforceable.

### Workstreams

- complete PDP/PEP coverage for all P0 side-effect boundaries
- canonicalize action envelopes
- stabilize principal, capability, resource, and contract binding
- unify policy reason codes and obligations
- move RunProof generation toward event projection
- create a durable event model
- establish verifier records as completion inputs
- formalize subagent delegation contracts
- build mutation proposal and diff-gate interfaces
- maintain performance targets for authorization decisions

### Exit gates

- 100% identified P0 boundaries pass through a PEP
- deny-by-default works under invalid, partial, or mismatched context
- authorization property tests cover normalization and scope boundaries
- action and decision records are reproducible from canonical inputs
- RunProof can represent success, failure, denial, cancellation, and inconclusive verification
- no TUI-specific state is required to enforce execution

## 2027 — Arcana SDK and durable runtime

### Objective

Make Arcana embeddable and resilient beyond the interactive CLI.

### Workstreams

- ship `@arcana/protocol`, `@arcana/sdk`, `@arcana/policy`, and `@arcana/conformance`
- add embedded, local-daemon, and CI runtime profiles
- implement durable event persistence and recovery
- introduce capability manifests and registration
- create evidence and artifact storage interfaces
- build offline RunProof validation
- ship observe, warn, approve, enforce, and locked adoption modes
- add MCP and GitHub Actions adapters
- expose verification and approval APIs

### Exit gates

- an external sample application embeds Arcana without the TUI
- a run resumes safely after process termination
- proofs validate offline
- the reference SDK passes Core and Policy conformance suites
- at least three non-Arcana tools are wrapped as capabilities
- governance can be introduced in observe mode without behavior changes

## 2028 — Execution platform

### Objective

Coordinate long-running, multi-agent, multi-environment work as durable execution graphs.

### Workstreams

- dependency-aware scheduler and bounded concurrency
- checkpoints, compensation, and rollback reporting
- reusable workflow and intent-contract registry
- independent verifier coordination
- model routing based on requirements, policy, cost, and historical quality
- budgets for tokens, cost, duration, retries, and delegation
- remote-worker protocol and fleet controls
- selective replay and dry-run support
- epistemic claim, assumption, and contradiction records
- organization policy distribution and approval routing

### Exit gates

- multi-hour runs survive disconnects and restarts
- multi-agent work preserves strict delegated authority
- success criteria are independently evaluated
- replay reports fidelity and dependency substitutions
- model-provider failure can reroute without violating policy
- workflows are reusable as versioned execution contracts rather than prompt bundles

## 2029 — Public protocol preview

### Objective

Extract proven execution semantics into a public, implementation-independent specification.

### Workstreams

- publish versioned protocol schemas and rationale
- define canonical JSON and resource identifier rules
- release standalone validator and negative conformance fixtures
- formalize RunProof, event-chain, approval, evidence, and verification semantics
- document privacy, redaction, and selective-disclosure profiles
- publish transport profiles for files, HTTP, and event streams
- establish compatibility and proposal processes
- build Python SDK and at least one non-TypeScript validator
- recruit design partners for independent proof production or consumption

### Exit gates

- at least one independent implementation passes Core conformance
- proofs produced outside Arcana validate in the reference validator
- protocol packages have no dependency on Arcana product packages
- schema evolution and compatibility rules are exercised through at least one minor release
- external implementers identify and influence specification changes

## 2030 — Ecosystem and organizational intelligence

### Objective

Develop an ecosystem of capabilities, verifiers, proof consumers, and reusable execution workflows.

### Workstreams

- capability registry and signing model
- verifier registry and trust metadata
- workflow publishing and compatibility declarations
- organization-specific execution memory with provenance and quality controls
- cross-run calibration and failure-pattern learning
- proof inspection and compliance integrations
- IDE, CI, infrastructure, and security-platform integrations
- remote attestation and transparency-log experiments
- cross-runtime continuation or selective replay

### Exit gates

- multiple third-party capability or verifier providers exist
- independent proof consumers provide value without Arcana Cloud
- cross-runtime continuation is demonstrated for a bounded workflow
- organizational memory reduces repeated failures in measured evaluations
- ecosystem artifacts have clear signing, versioning, and revocation semantics

## 2031 and beyond — Execution interoperability layer

### Objective

Make governed execution portable across products and organizational boundaries.

### Candidate directions

- signed execution packages exchanged across organizations
- procurement and compliance acceptance of machine-verifiable execution evidence
- industry-specific profiles for software delivery, security, research, infrastructure, and regulated operations
- federated identity and capability delegation
- selective disclosure and privacy-preserving proof exchange
- execution-quality reputation based on verifiable outcomes
- simulation and alternative-plan comparison before consequential execution
- decentralized or multi-party execution where no single organization controls the full run

### Maturity signals

- protocol governance includes multiple independent implementers
- Arcana-compatible execution artifacts are accepted by external systems
- organizations adopt the protocol without adopting Arcana products
- compatibility decisions prioritize ecosystem stability over product convenience

## Cross-cutting programs

### Security

Every year includes threat modeling, enforcement coverage, supply-chain integrity, secret handling, sandbox hardening, fuzzing, and external review.

### Performance

Governance must remain inexpensive enough for high-frequency tool execution. Event capture and proof projection should support streaming and batching without weakening semantics.

### Developer experience

The governed path must be the easiest path. APIs should make authority, evidence, and verification visible without forcing developers to understand every protocol detail initially.

### Research

Maintain evaluation suites for:

- policy correctness
- capability-boundary escape
- verifier reliability
- epistemic calibration
- replay fidelity
- cost and token efficiency
- long-horizon recovery
- multi-agent delegation safety

## Kill criteria

Arcana should reconsider or narrow the protocol strategy if:

- external developers cannot use the SDK without extensive Arcana-specific knowledge
- proof objects are too large or complex for practical use
- independent implementations reveal that core semantics depend on hidden runtime behavior
- governance latency or friction prevents adoption
- the protocol duplicates adjacent standards without adding meaningful execution semantics
- no external proof producer or consumer emerges after sustained SDK adoption efforts

Stopping or narrowing a protocol effort is preferable to maintaining a fictional standard.

## Strategic scorecard

Track progress through outcomes rather than feature counts:

- enforcement-boundary coverage
- proof validation rate
- run recovery success rate
- unsupported-claim rate
- verifier disagreement rate
- replay fidelity
- mean approval burden per useful outcome
- cost per verified completion
- repeated-failure reduction
- number of external SDK integrations
- number of independent protocol implementations
- percentage of usage not involving the Arcana TUI
