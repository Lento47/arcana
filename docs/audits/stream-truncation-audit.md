### A1 — Native silent cut (v2 corrected)

Chain: `packages/llm/src/protocols/openai-chat.ts:449-457` — `finishEvents` suppresses the terminal event when `state.finishReason` is undefined (`if (reason) Lifecycle.finish(...)`) → `packages/llm/src/route/client.ts:272-288` — `streamPrepared` treats a clean EOF without a terminal event as **success** → `packages/engine/src/session/processor.ts:1243` returns `"continue"` with no error → the message persists with `finish=None`.

**v1 correction:** `prompt.ts:1520` (`finish ?? "stop"`) applies **only** to the structured-output branch (`if (structured !== undefined)`); it does not mask the normal path. A silent cut leaves a durably non-terminal message with partial text, no error, no retry, no recovery.

The AI SDK path is **not** affected: `ai-sdk.ts:111-124` always synthesizes a `finish` event, and `error` parts fail the stream (`ai-sdk.ts:264-265`) — matching `.hermes/docs/ai-sdk` `50-error-handling.mdx` best practice (streams with error support must surface `error`/`abort` parts).

**Design-compliance note (v3):** this is an *epistemic* defect, not just a UX defect. A turn that ends without a terminal event leaves the run lifecycle evidence incomplete — the Phase A/B trace must never claim completeness with a missing terminal lifecycle event (Playbook §A3/B6; Master Spec §16.4 "evidence emission failure marks trace DEGRADED or UNAVAILABLE"; TUI-1.1 exit "missing evidence appears DEGRADED, never healthy"). The F-A1 fix (synthesize `finish("unknown")`) implements the Playbook D6 principle verbatim: **record the indeterminate outcome (UNKNOWN) rather than blind-retry or pretend success**. It also matches `packages/llm/AGENTS.md` protocol rule: "emit exactly one terminal `finish` event for each completed response... use `stream.onHalt` when the final event must be flushed after the framed stream ends."

**SDK-doc evidence (v4)** — the AI SDK docs independently confirm every link of this chain:
- The SDK's own transport treats "stream closed without a `finish` event" as **incomplete** and reconnects: `04-ai-sdk-workflow/02-workflow-chat-transport.mdx:199-204` ("Detect interruption: if the stream closes without a finish event... the transport knows the response is incomplete"), `04-ai-sdk-ui/21-transport.mdx:161`.
- `finishReason` is **undefined on the wire when the model doesn't provide one** — a normal state, not an error: `07-reference/02-ai-sdk-ui/01-use-chat.mdx:312-317` ("Undefined if the finish reason was not provided by the model").
- The terminal `finish` event is **not guaranteed**: `toUIMessageStream`'s `sendFinish` defaults true but can be disabled (`02-stream-text.mdx:4061-4065`); on error the terminal part is `error`, on abort it's `abort`.
- Naming note: AI SDK v6 **removed** the `"unknown"` finish reason, merging it into `"other"` (`08-migration-guides/24-migration-guide-6-0.mdx:522-524`). Arcana's own `FinishReason` schema (`packages/llm/src/schema/ids.ts:36`: `"stop" | "length" | "tool-calls" | "content-filter" | "error" | "unknown"`) is independent and keeps `"unknown"` — F-A1's `finish("unknown")` is schema-valid; do not rename to "other".
- **Arcana's own normative text (v4, verbatim)** — `packages/llm/AGENTS.md:277-278`: "Parser state owns terminal information. The state machine records finish reason, usage, and pending tool calls; **emit one terminal `finish` event (or `provider-error`) for each completed response**." — with no exception for a missing reason; plus the review checklist `:289`: "Does stream parsing emit stable common events without leaking provider event order to callers?" F-A1 is implementing an in-repo normative rule, not inventing one.

**SDK v7 source evidence (v5)** — `packages/ai/src` (v7.0.46) verified at code level:
- The consumer-facing `finish` part is **guaranteed on all normal-completion paths**: emitted exactly once in the step TransformStream flush before `closeStream()` (`generate-text/stream-text.ts:2455-2462`); when the provider stream ends without a terminal chunk, the SDK **synthesizes `finishReason: 'other'`** (`stream-text.ts:2153`, `:2292-2299`).
- If the provider stream ends without a terminal chunk **and without any output**, the SDK synthesizes an `error` part (`NoOutputGeneratedError`, `stream-text.ts:2332-2343`) — so a bare EOF is never silently "successful" on the AI SDK path.
- Abort surfaces as an `abort` part then clean end — **no `finish` part, no throw** (`stream-text.ts:1510-1556`); timeouts (firstChunkMs/chunkMs) surface as `abort` parts too. SDK v7 retires `'unknown'` in the core (`types/language-model.ts:75-81`); `'unknown'` survives only in the legacy v2 spec and is mapped `unknown → other` (`as-language-model-v3.ts:80-87`).
- **Arcana adapter already implements the F-A1 pattern**: `packages/engine/src/session/llm/ai-sdk.ts:21-23` maps any reason outside Arcana's union (incl. SDK `'other'`) to `"unknown"`, and `:111-115` synthesizes `LLMEvent.finish` on the SDK `finish` part. The native runtime is the **only** runtime that suppresses the terminal event — F-A1 makes both runtimes converge (per `packages/engine/src/session/llm/AGENTS.md`: "Both runtimes converge on the same `LLMEvent` stream").
- **Residual (v5):** the adapter **silently drops `abort` parts** (`ai-sdk.ts:267-272` → `Effect.succeed([])`) — no terminal event on abort. Correctness then depends on the processor's `halt()` interruption landing (A7). F-A7a verification must include an abort test proving the message ends `finish="error"`, never clean-EOF-without-finish.

**v6 anchors:** (1) `PHASE-D7-LOCAL-DISTRIBUTED-AUTHORITY.md:52` defines trace health `INCOMPLETE` = "Required events not yet recorded" — the precise state a `finish=None` turn occupies; the hard gate "False COMPLETE assurance profiles = 0" (`phase-c-evaluation.md:48`, `PHASE-C-MILESTONE.md:53`, Playbook:581) forbids presenting that state as complete. (2) Synthetic-event precedent in-repo: M5 publishes ML annotation as a synthetic `Text.Delta` for streaming clients (`qa-fixes-2026-07-10.md:256`) — F-A1's synthetic terminal `finish("unknown")` is the same documented pattern, not an invention.

### A7 — `halt()` leaves `finish=None` (stall-audit mechanism B, live-verified)

`processor.ts:1127-1167`: the generic error path sets `assistantMessage.error` but never `finish="error"` — only the ContextOverflow-with-compaction-disabled branch (`:1138-1139`) sets it. Live-verified (stall-audit addendum, direct sqlite query): aborted/errored turns leave `finish=None`, `time.completed` set, partial text. The TUI sync subscriber never branches on `finish` (`sync.tsx:387-427`), and no reconcile trigger is keyed to turn lifecycle (list of triggers in stall-audit §Mechanism B: heartbeat-gap / missing-part / reconnect / stream-reset / manual — none turn-terminal).

**Design-compliance note (v3):** the Master Spec session event family is `session.started / input.admitted / model.started / session.completed / session.crashed` (§16.3). A turn ending with `finish=None` is neither `completed` nor `crashed` — an indeterminate state with no recorded terminal event. F-A7a (`finish="error"`) restores the terminal `session.crashed` semantics on the wire and in the DB, and F-A7b (turn-end reconcile) makes the TUI converge to the recorded outcome — both required by the doctrine "the TUI observes engine truth, never invents it" (Master Spec §8.1) and the observability gate "failures cannot silently appear healthy" (Playbook §4.8).

**Official fix-spec alignment (v5):** this finding is exactly **F1** of `TUI-2.1-NEXT-STEPS.md` (PHASE A, operator permission required): "engine: terminal `finish="error"` on every non-clean turn end. generic error path never sets `finish`; DB-verified `finish=None + error` on BOTH stream-error and abort paths (audit addendum)"; abort path observed `error=Aborted` at 03:08:05. The fix location matches: `processor.ts` `halt()` — copy the `finish="error"` line from the ContextOverflow branch (`:1138-1139`). **F2** (same doc) = F-A7b, with a documented SolidJS lesson: "do NOT pass the live message object into store merges — follow the `aedd96dc` `structuredClone` lesson" (passing `msg` by reference made SolidJS `reconcile` see no diff — **"streaming never ended"**). F-A7b must merge a `structuredClone` of the durable message, never the live object.

### A8 — Connection storm (stall-audit mechanism C; mechanism corrected in v4)

- **v4 correction:** the "dead sockets pooled on EOF" claim is **retracted** at the client layer — `serverSentEvents.gen.ts:220` exits the generator cleanly on EOF and `:217` releases the reader lock; the response body is done, so the fetch connection is not held by this code. The storm's code mechanism is elsewhere.
- Remaining verified mechanism: `packages/engine/src/server/server.ts:210-235` — server created with **no** `keepAliveTimeout`/`headersTimeout`/`maxConnections`. Half-open SSE sockets from dead/replaced TUI processes (daemon restarts, kill, network drop) accumulate server-side until the kernel notices the dead peer; each new TUI reconnect + REST reconcile adds a new socket. Empirically ~130 = Bun per-origin fetch pool cap 128, so the storm is **real** (stall-audit observation); the saturating population is server-side half-open sockets, not client EOF pooling.
- **Daemon-docs support (v4):** no doc in `.hermes/docs/daemon/` recommends HTTP keep-alive timeouts (library is supervisor-level); the storm justification stands on HTTP hygiene + the empirical observation. Two new daemon-doc constraints: (1) **SIGPIPE masking** — systemd `systemd.service.5.md:778-783` classifies SIGPIPE death as a *clean* exit; a daemon killed while writing to a stale SSE client silently defeats `Restart=on-failure` policies → daemon must ignore SIGPIPE / handle EPIPE writes. (2) **FDSTORE is the only way active streams survive a daemon restart** (`sd_notify.3.md:291-301`); Arcana's daemon does not fd-store, so **every daemon restart necessarily terminates every active stream** → client reconnect-on-EOF is mandatory, not advisory.
- Worker mode (zero TCP) is immune.

### A10 — Watchdog trip poisons the reconnect loop's AbortController (new in v4, HIGH)

`packages/tui/src/context/sdk.tsx` — one `AbortController` (`ctrl`, created once per `startSSE` at `:164`) is **reused across every reconnect attempt** in the loop (`:169-231`, `sdk.global.event({ signal: ctrl.signal })` at `:176-177`). The watchdog trips `sse?.abort()` (`:59`) — permanently aborting `ctrl`. Consequences:

1. `serverSentEvents.gen.ts:101` (`if (signal.aborted) break`) — with an already-aborted signal the generator **breaks before fetching**; `sdk.global.event()` resolves with an **empty stream, silently, every attempt**.
2. The loop iterates: empty stream → backoff → `sse.reconnected` emitted (`:221-230`) **even though nothing reconnected** → session route REST-resyncs on every tick (redundant requests — Playbook WS-P2 "redundant request count = 0" violation) → repeat. The SSE channel **never recovers**; live deltas are permanently frozen after one watchdog trip.
3. The heartbeat gap detector (P10) never fires either — it keys on heartbeat events that now never arrive. The only rescue is a manual `startSSE` (mount) or the on-view-resume resync.

**Doc-code divergence (v4):** `docs/architecture/command-spine-ui.md` §Stream liveness contract (lines 135-161) documents the *intended* behavior: "trip aborts only **the current attempt**; the loop reconnects and emits `sse.reconnected`" with a "~35s" recovery promise. The code does not implement it: the trip aborts **all future attempts**. This is a documented-contract violation, and the fix restores the doc's promise. The rest of the documented contract is code-verified: 10s heartbeat (`event.ts:109` `Stream.tick("10 seconds")`), 30s watchdog = 3 missed heartbeats (`sdk.tsx:19` `SSE_SILENT_DEATH_MS = 10_000 * 3`), no Last-Event-ID replay → full REST resync as the gap-closer.

**Related backoff gap (v4):** the reconnect backoff (`sdk.tsx:85,90,213`: `retryDelay=1000`, `maxRetryDelay=5000`, `min(1000 * 2 ** (attempt-1), 5000)`, **unbounded attempts — deliberate**, per `TUI-2.1-FREEZE-EXECUTION-PLAN.md:171` "unbounded attempts = deliberate (local daemon may restart)") has **no jitter**; Playbook TUI-1.1/architecture norm (playbook line 1221) and `TUI-2.1-NEXT-STEPS.md` P2-2 both require "exponential backoff **and jitter**". Multiple subscribers reconnecting together will synchronize their retries. F-A8b adds jitter while keeping the ≤1/sec gate (`FREEZE-EXECUTION-PLAN.md:140`: "SSE reconnect rate ≤ 1/sec, exponential backoff + jitter" — current 1s→5s schedule already meets ≤1/sec).

**Doc-mandated fix spec (v5):** A8+A10 are exactly **F3 + F4** of `TUI-2.1-NEXT-STEPS.md`: F3 = `createServer({ keepAliveTimeout: 5_000, headersTimeout: 10_000 })` with verify "cold-daemon boot → ESTABLISHED decays to ≤10 within ~15s of idle"; F4 = "new `AbortController` per attempt, abort prior on stream end (destroy path `serverSentEvents.gen.ts:139-145`; clean-EOF pools the socket at `:220`). **Complement if cancel does not destroy: `Connection: close` on the SSE response (`handlers/event.ts:167-174`)**". Note: F4's "clean-EOF pools the socket" is connection-level pooling (a cleanly finished response returns the TCP conn to the fetch keep-alive pool — consistent with v4's correction that the generator itself exits cleanly); the doc-mandated `Connection: close` contingency covers the case where cancel does not destroy the pooled connection. **The documented smoke expectation is currently broken by A10:** `TUI-2.1-MANUAL-SMOKE-TEST.md` §10.3 expects "within ~35s the TUI reconnects (`sse.reconnected`), the session REST resync fires, text + verbs restore... No truncation persists after the heal" — today the post-trip loop emits `sse.reconnected` but never reconnects; the smoke test would fail at 10.3 until F-A8b lands.

**v6 note:** the fix's target files are contractual substrate — `TUI-MIGRATION-CONTRACT.md:179-180` KEEP list includes `context/sdk.tsx`, `context/sync.tsx`, `context/event.tsx`, `@arcana/sdk/v2` — so F-A8b/F-A7b modify the maintained, contract-protected surface (no migration conflict).

### A3 — Retry duplicates (unchanged from v1; doc evidence added in v4)

`processor.ts:1205-1236` — `Effect.retry(SessionRetry.policy(...))` re-runs the entire `process` effect (including `llm.stream`) on retryable mid-stream failure (429, 5xx, network drop — the **default AI SDK path**). Text/reasoning parts created by attempt 1 are never pruned; attempt 2 appends new parts to the same assistant message. Durable "cut then repeat" artifact; `flushV2Fragments` already marked the partial fragment `Text.Ended` (dashboard-side inconsistency, known limitation). Not addressed by any fix-log round.

**Doc evidence (v4):**
- The AI SDK provides **no dedupe guarantee** across retries: retries are transport-level (`maxRetries` default 2, `25-settings.mdx:110-116`); the UI error-handling doc prescribes manual partial purging — "remove both the partial assistant response and its user message" (`04-ai-sdk-ui/21-error-handling.mdx:116-118`). Engine-side pruning (F-A3) is therefore the only correct place to dedupe.
- Existing defense-in-depth, code-verified: the **M6 prefix-based edit guard** (`qa-fixes-2026-07-10.md` §M6; `packages/engine/src/cli/cmd/run/session-data.ts:468-473`) rejects any delta where `prev.startsWith(next)` (truncation/echo-strip) and accepts only appends — a retried delta cannot shrink the accumulated text. F-A3 operates upstream of this guard (prunes whole parts before they are persisted) — complementary, not conflicting.
- Retry-budget constraint: `security-audit-2026-07-14.md:336-341` (M21, still open) flags unbounded tool retries. F-A3 must **not** add retries — only prune failed-attempt parts; `SessionRetry.policy` remains bounded (Playbook WS-P2 "never blind-retry"; Master Spec §15.2 durable retries).
- **v7 correction (audit error fixed):** "`SessionRetry.policy` remains bounded" is **wrong on attempts** — `retry.ts:208-226` is `Schedule.fromStepWithMetadata` with **no `Schedule.recurs` cap** → unbounded attempt count (delay capped at 30s via `RETRY_MAX_DELAY_NO_HEADERS`, or a `retry-after` header up to the 32-bit ceiling; error class gated by `retryable()`, `:88-179` — 5xx always retried, 429 only when explicitly `retryable:true`). This matches M21's still-open unbounded-retry finding, now extended from tools to the stream path. F-A3's constraint is unchanged (prune only, never add retries), but the prune must be correct across **any** number of attempts — the part-index snapshot at `process` start (`:1209` `set` callback) handles that by construction. The agent-level budget remains `maxRetries: 2` (`docs/object-schemas.md:37`); enforcing it on the engine policy is tracked alongside M21, not in this fix.

**SDK v7 source evidence (v5):** SDK retries are **request-level, entirely before any streaming reaches the consumer** — `retry(async () => streamLanguageModelCall({...}))` at `stream-text.ts:2013-2079` covers only prompt conversion + `doStream` + pre-output body consumption; `shouldRetry` accepts only `APICallError.isRetryable` / `GatewayError.isRetryable` (`provider-utils/src/retry-with-exponential-backoff.ts:80-83`), and **abort errors are rethrown without retry** (`:89-91`). Mid-stream transport failures occur after the retry wrapper has returned and are **never retried by the SDK** — the engine's `Effect.retry` (processor.ts:1205-1236) is the **only** dedupe point, exactly where F-A3 prunes. **P2-4 discipline** (`TUI-2.1-NEXT-STEPS.md`): 429/503 currently fail closed (`map-upstream.ts:77,115`) — "no blind retry (good), but no bounded retry+backoff (resilience gap)"; F-A3 must not change this stance, only prune on the engine-side retry that already exists.

**v6 anchor:** the AgentContract schema bounds retries at the agent level — `docs/object-schemas.md:37` `"maxRetries": 2` — so the retry budget F-A3 operates within is a documented contract default (matching the AI SDK's transport default); F-A3 adds no retries, it only prunes within this bounded budget.

### A2 — Queue hardening (reframed from v1)

`packages/engine/src/server/routes/instance/httpapi/handlers/event.ts:53-58` — the listener offers **every event from every directory/workspace** into every subscriber's `Queue.sliding(512)`; the workspace filter runs downstream (`:75-79`). Foreign noise (file-watcher events, other sessions' 500ms `PartUpdated` flushes) can evict a subscriber's own deltas. **Not observed in production** (stall audit), but a code-level weakness: foreign events should never consume a subscriber's budget. Wire sequence assignment (post-filter, `:102-107`) is untouched by the fix.

**Design-compliance note (v3):** the per-subscriber queue is the contract between the daemon and the SDK/TUI (Master Spec §6.3 daemon model: daemon owns durable services, TUI is a projection). Filtering before offer keeps the projection contract gapless per subscriber with no behavior change on the wire — compliant with Playbook WS-P2 (bounded retries, single connection, no amplification).

### A5 — Gateway truncation (documented-behavior upgrade)

`gateway.md:49` and `gateway.md:79` document "truncated automatically" at 2000 (Discord) / 4096 (WhatsApp). Code: `packages/gateway/src/platforms/discord.ts:31,47` (`slice(0, 2000)`); `whatsapp.ts:165` (`slice(0, 4096)`). Telegram already chunks. Users see a silent tail loss with no continuation.

**v6 precedent:** the repo already has the honest-tail pattern — `CHANGES` QA-fix transcript: `resultStr.slice(0, TOOL_RESULT_MAX) + "\n...(truncated N chars)"` (count-suffix marker instead of silent slicing). F-A5 should mirror it: append a drop marker (and optionally a continuation/backfill reference) on the gateway side, so a missing tail is marked, never silently absent. **v7:** the pattern is pervasive in the engine itself — `message-v2.ts:50-53` `[Tool output truncated for compaction: omitted N chars]` (count-suffix), `compaction-assemble.ts:111` `…[truncated for compaction summary]`, `compaction.ts:1136` `\n... [truncated]`, `compaction-strategy.ts:67` — the gateway fix adopts an existing house style.

### A4 — Compaction cut (deferred, confirmed by design)

`session-compaction.md`: threshold 85%, `reserved: 20000` ("hard ceiling reserve so output still fits"), "Auto compact never kills the agent turn". The mid-stream cut (`processor.ts:1187-1191` `Stream.takeUntil(() => ctx.needsCompaction)` + `runDrain`) is event-boundary-safe; the trigger delta is fully processed before the halt. Artifact: the last text part remains durably mid-sentence. Optional polish (trim to sentence boundary / mark `metadata.interrupted`) — not a correctness fix. **Constraint (v3):** any polish must NOT rewrite the already-persisted part text or the compaction input — Master Spec §14.3 ("compaction must not erase security events or rewrite RunProof history") and §16.4 (append-only, "historical outcomes are not rewritten"). A `metadata.interrupted` marker is compliant; text rewriting is not. **Doc invariant (v4):** `arcana-durable-execution-memory-context-continuity.md` step 5 ("Never split an event or serialized message in the middle") and invariants 7 + append-only chain (§A3: "Failed transactions create no partial event") — the event-boundary safety of the cut is a hard, documented invariant, and it already holds; the deferred polish must keep it.

### A9 — O(N²) SSE parser under large events (perf-gate risk, new in v3)

`packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts` — documented in `TUI-2.1-SSE-STALL-REPORT.md` §3 as "O(n²) buffer pattern (`buffer += value` + regex replace + split per read) but not a correctness bug at tested volumes". Master Spec §8.4/Playbook TUI-1.6 perf gates (10,000-entry sessions, frame render p95 < 16.7ms, first model token p95 < 1s) make this a latent gate risk for very large tool outputs (100KB+ events). Not a truncation defect; tracked as P13-adjacent performance item. **Context (v5):** the blast radius is bounded by design — tool outputs are capped (`ADR-0002` + `arcana-performance-optimization-foundation.md`: `maxOutputChars` 2k/child, `maxSynthesisChars` 8k parent, RW-01 bounded long output); the largest observed single part is ~7.8k chars (DAEMON-ROOTCAUSE-AUDIT). Risk concentrates on multi-MB single parts (e.g., pasted file dumps), keeping this LOW.

### A6 — Reconcile visual jump (deferred, cosmetic)

A heartbeat-gap reconcile landing mid-generation replaces part text with the durable lag (≤500ms) then live deltas re-type it. Correctness is sound (`lastApplied` advances only on successful apply; no duplication). Optional polish: suppress reconcile while the part is actively streaming.
