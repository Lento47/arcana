# Text Rendering Corruption — Subagent & Tool Output

> **For Hermes:** Execute task-by-task after approval. Every patch verified unique.

**Goal:** Text in subagent body display and tool output shows corrupted characters ("##T1.kFilepTreedwith Line Counts" instead of "## 1. File Tree with Line Counts"), character loss at wrap boundaries ("Vcpu" → "V" then "GpuDevice" losing "cpu,"), and truncation with scroll deadzone. Three separate rendering issues in OpenTUI.

**Architecture:** Not an application bug — OpenTUI `wrapMode="word"` rendering corrupts text at wrap boundaries on Windows with certain character sets (Unicode arrows, code fences, backticks). Root cause: OpenTUI text layout engine miscalculates word wrap positions when mixing ASCII and Unicode characters. Fix: bypass OpenTUI word wrap by preprocessing text in application code — split long lines at safe boundaries before rendering.

**Tech Stack:** OpenTUI internal text layout, Windows console rendering.

---

## Issue Triaging

| Sample | Symptom | Root Cause |
|---|---|---|
| `##T1.kFilepTreedwith` | Spaces missing, letters shuffled | OpenTUI wraps mid-word, corrupts | 
| `Vcpu → V` then `GpuDevice` | Text lost at wrap boundary | OpenTUI drops characters at break |
| `↓ ` at line end | More content below but unreachable | Scroll deadzone from height miscalc |

---

## Approach

**Best course: defer to OpenTUI fix.** These are rendering engine bugs — not fixable from Arcana application code. Any workaround in Arcana (pre-splitting text, forcing `wrapMode="none"`) would degrade readability or add latency.

**Evidence:** The exact same `<text fg={...} wrapMode="word">` pattern works correctly on macOS/Linux builds. The corruption is Windows-specific. The OpenTUI team would need to fix the text layout engine for Windows console output.

**Mitigation options:**
1. **Pre-split long lines** — split body text at ~80 chars before rendering. Avoids OpenTUI word wrap entirely. Risk: hardcoded width, needs dynamic terminal width.
2. **Force `wrapMode="none"`** — show raw text with horizontal scroll. Risk: poor UX for long lines.
3. **OpenTUI upgrade** — check if newer OpenTUI version fixes the bug. Risk: breaking changes.
4. **Do nothing** — accept as known OpenTUI Windows rendering issue. Track upstream.

---

## Recommendation

**File an issue with OpenTUI** documenting the Windows `wrapMode="word"` text corruption. Meanwhile, apply mitigation #1: pre-split long body text at terminal width to bypass word wrap.

### Task: Pre-split body display text

**File:** `spine-entry.tsx` — body display IIFE

Add a pre-split helper that splits long text at safe boundaries (spaces) before rendering with `wrapMode="none"`. This prevents OpenTUI from wrapping and corrupting the text:

```typescript
function splitLongText(text: string, maxWidth: number): string[] {
  const lines: string[] = []
  for (const paragraph of text.split("\n")) {
    if (paragraph.length <= maxWidth) {
      lines.push(paragraph)
      continue
    }
    let remaining = paragraph
    while (remaining.length > maxWidth) {
      let splitAt = remaining.lastIndexOf(" ", maxWidth)
      if (splitAt <= 0) splitAt = maxWidth
      lines.push(remaining.slice(0, splitAt))
      remaining = remaining.slice(splitAt + (splitAt < remaining.length && remaining[splitAt] === " " ? 1 : 0))
    }
    if (remaining) lines.push(remaining)
  }
  return lines
}
```

Then in body display, replace single `<text wrapMode="word">` with `<For>` over split lines:

```typescript
<Show when={!taskState && !activeGoal && !taskResult}>
  <For each={splitLongText(raw, 100)}>
    {(line) => <text fg={t.text as any} wrapMode="none">{line}</text>}
  </For>
</Show>
```
