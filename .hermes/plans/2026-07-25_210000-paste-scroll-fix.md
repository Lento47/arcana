# Paste Reference Rendering + Text Overflow Scroll Fix

> **For Hermes:** Execute task-by-task.

**Goal:** Two issues: (1) `[Pasted text #N: X lines → path]` references show as raw text instead of loading paste content. (2) Long text blocks prevent scrolling to bottom of chat.

---

### Issue 1: Paste references not rendered

**File:** `session/index.tsx` — `GenericTool` formatted output

Detect paste reference pattern `[Pasted text #N: X lines → path]` and try to load the file content. Add a new `FormattedOutput` variant:

```
| { type: "paste"; path: string; lineCount: number; defaultText: string }
```

Detection in `formattedOutput` memo (before XML check):
```typescript
    // Paste file references: [Pasted text #N: X lines → path]
    const pasteMatch = raw.match(/^\[Pasted text #\d+: \d+ lines → (.+)\]$/)
    if (pasteMatch) {
      const filePath = pasteMatch[1]!
      const lineCount = parseInt(raw.match(/ (\d+) lines/)![1]!)
      // Don't load file here — memo should be sync. Defer to render.
      return { type: "paste", path: filePath, lineCount, defaultText: raw }
    }
```

Then in the render `<Switch>`, add a `<Match>` that loads and shows paste content. But loading files is async — need a signal-based approach:

```typescript
// In GenericTool, add state for paste content:
const [pasteContent, setPasteContent] = createSignal<string | null>(null)

// ... in XML detection before JSON.parse:
    if (pasteMatch) {
      const filePath = pasteMatch[1]!
      // Load paste file content
      const path = require('node:path')
      const fs = require('node:fs')
      // ...
    }
```

**Scope decision:** Loading paste files from TUI requires fs access, which may not be available in all contexts. The paste file path uses Windows paths (`L:\hermes\pastes\...`). The TUI runs in the same process as the engine and has filesystem access.

**Simpler approach:** Add a "view paste" button or just display the reference nicely (with line count and path) instead of trying to load file content inline. This avoids async IO complexity.

### Issue 2: Long text blocks prevent scrolling

**Root cause:** `viewportCulling={true}` with very tall content entries. The scrollbox estimates heights for culled entries. Large text blocks (50+ lines) have inaccurate height estimates, causing scroll position to be wrong.

**Fix:** Revert to `viewportCulling={false}` for now, or add a maximum entry height so no single entry dominates the viewport.

Actually — the simpler fix: the `stickyScroll` + `stickyStart="bottom"` interaction with culling. When new content appears at the bottom and the entry is tall, the scrollbox scrolls to show it, but then the estimated height changes as the entry enters the viewport (gets measured), causing the scroll to jump back.

**Fix:** Keep `viewportCulling={true}` but increase the estimated height for entries with large body text. OR, more pragmatically: ensure paste content is collapsed by default (not expanded) so it doesn't flood the viewport.

**Decision:** Keep `viewportCulling={true}`. The paste reference shows as ONE LINE (collapsed). User expands to see content. The collapsed state doesn't cause scroll issues.
