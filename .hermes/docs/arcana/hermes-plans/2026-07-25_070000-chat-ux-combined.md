## Regression Analysis

### REG-1: `viewportCulling={true}` may break `stickyScroll` during streaming ⚠️ NEW

When the assistant streams markdown, new text chunks arrive continuously. `stickyScroll` relies on scroll height changes to auto-scroll. With `viewportCulling`, culled entries use ESTIMATED heights. When a new entry is rendered at the bottom, the scrollbox measures it. If the measured height differs from the estimate, the scroll position may jump.

**CULL-1a (streaming position jump):** The streaming entry at the bottom changes height as text arrives. With culling, only THIS entry is re-measured — other entries use cached/estimated heights. This is actually BETTER than `false` (where ALL entries re-layout on every chunk). **Acceptable.**

**CULL-1b (estimated height mismatch):** When scrolling through previously unrendered content, OpenTUI estimates child heights. On first scroll, the estimate may be off, causing slight position correction. Subsequent scrolls use measured heights. This is the standard virtual-list trade-off. **Acceptable.**

**CULL-1c (expanded entries):** When an entry is expanded (showing full output), then culled off-screen, and later scrolled back — it must re-render expanded. The `entryExpanded(entry())` signal at line 293 tracks expanded state in a Set, independent of render state. When the entry re-renders after unculling, `entryExpanded` returns `true` from the Set. **Verified — no regression.**

### REG-2: Scroll button needs polling, not `createEffect` ⚠️ FIXED IN PLAN

The `ScrollBoxRenderable` properties (`y`, `scrollHeight`, `height`) are mutable renderable properties, NOT SolidJS reactive signals. A `createEffect(() => { scroll.y })` runs ONCE and never re-triggers on scroll.

**Fix:** Use `setInterval` (matching the existing pattern at session/index.tsx:581). Poll every 250ms. Add `onCleanup` to clear the interval.

**Why this works:** The existing `setInterval` at line 581 has been polling `scroll.y` for infinite scroll (load older messages). The same pattern works for the button. Added to plan.

### REG-3: Scroll button `onCleanup` interval leak ⚠️ FIXED IN PLAN

Without `onCleanup`, the interval keeps running after session switch, polling a destroyed scrollbox (`scroll.isDestroyed === true`). The guard `if (!s || s.isDestroyed) return` prevents errors but the interval still consumes CPU.

**Fix:** Store interval ID, clear in `onCleanup`. Added to plan.

### REG-4: Shell reactivity — `status()` memo depends on `props.part.state.status` ⚠️

If `props.part.state.status` is NOT reactive (plain property on a plain object), `createMemo(() => props.part.state.status)` won't re-run. In SolidJS, component props are wrapped in a shallow Proxy. `props.part` is tracked (the reference). `props.part.state.status` — two levels of access — the Proxy tracks `props.part` and `props.part.state`, but does it track `.status` at depth 2?

SolidJS `props` proxy tracks ALL nested accesses (deep proxy). So `props.part.state.status` IS reactive. The issue is more likely that `ToolPart` component doesn't re-render when the underlying store changes because `sync.data.part[messageID]` updates bypass the prop chain.

**Mitigation:** The explicit `createMemo` forces SolidJS to subscribe to `props.part.state.status`. If it IS reactive, the memo updates. If NOT, it still creates a dependency that may trigger on parent re-render. Either way, it's strictly better than the current getter-only approach.

**Fallback if fix doesn't work:** Wrap `part.state` in `createStore`. Out of scope for this plan.

### REG-5: Shell `output()` shows "" for pending tools — user sees empty output area

When status is "running" and `metadata` is `{}`: `stringValue(undefined)?.trim() ?? ""` → `""`. The `<Show when={output()}>` hides children (empty string is falsy). User sees command line but no output text. This is correct behavior — output hasn't arrived yet. When output arrives during "running" state, the metadata getter returns it, output memo updates, `<Show>` shows it. ✅

### REG-6: Match condition changed from `output !== undefined` to `status !== "pending"` — broadens match scope

Previously, the BlockTool only rendered when `metadata.output` was a string. Now it renders whenever status is NOT "pending" — including "running" and "completed". During "running", output may be `""` (empty). The `<Show when={output()}>` hides it, and `<Show when={isCompleted()}>` only shows "(no output)" when completed. During running: command line visible, no output visible, spinner in title. This is correct behavior. ✅

### Task 2: Add scroll-to-bottom button with polling (4 min)

**Objective:** Floating "↓" button appears when scrolled up > half page. Uses `setInterval` polling (not `createEffect`) because scrollbox properties are not SolidJS-reactive.

**File:** `packages/tui/src/shell/command-spine/command-spine-shell.tsx`

**Step 2a: Add signal + polling.** After `let scroll` (line 75), add:

```tsx
  const [showScrollButton, setShowScrollButton] = createSignal(false)
  let scrollPollInterval: ReturnType<typeof setInterval> | undefined

  // Poll scroll position every 250ms — scrollbox props are NOT SolidJS-reactive
  onMount(() => {
    scrollPollInterval = setInterval(() => {
      const s = scroll
      if (!s || s.isDestroyed) return
      const distanceFromBottom = s.scrollHeight - s.y - s.height
      setShowScrollButton(distanceFromBottom > s.height / 2)
    }, 250)
  })

  onCleanup(() => {
    if (scrollPollInterval) clearInterval(scrollPollInterval)
  })
```

**Step 2b: Wrap scrollbox in position container + add floating button.**

The scrollbox and button need a `position="relative"` wrapper so the absolute button tethers to the scrollbox area, not the screen bottom (which would overlap the SpinePrompt).

## Risks and Open Questions

1. **Viewport culling may cause first-scroll jitter.** Entries not yet rendered use estimated heights. First scroll through unseen content may have slight position correction. Subsequent scrolls use measured heights. Standard virtual-list behavior.

2. **250ms polling overhead.** One `setInterval` reading three integer properties. Negligible (<0.01% CPU).

3. **Two intervals in session route.** The existing `scrollInterval` at session/index.tsx:581 also polls at 250ms. This is a separate concern (loading older messages). The Shell's interval is separate. Both are lightweight.

4. **Shell reactivity fallback.** If `status()` memo doesn't trigger re-render (because `props.part.state.status` isn't reactive), the Shell component stays broken. The next step would be wrapping `part.state` in `createStore` — but that requires changes to the data layer, not just the TUI. **Risk acknowledged; plan includes this as the first attempted fix.**
