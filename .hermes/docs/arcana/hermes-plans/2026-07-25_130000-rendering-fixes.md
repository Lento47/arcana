# TUI Rendering Issues — Code Blocks, Structured Output, Never-Ending Working

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Fix three TUI rendering problems: (1) code blocks in chat render with broken `│` separator bars, (2) structured tool outputs (XML/JSON like `<active-goal>`) render as raw text instead of formatted, (3) "Working" shimmer/pending state never transitions to idle.

**Architecture:** Issue 3 is the critical one — trace the `pending`→`idle` transition chain in `session/index.tsx` and `turn-lifecycle.ts`. Issues 1-2 are markdown/tool output rendering in `SpineProse` and `GenericTool`.

**Tech Stack:** SolidJS, OpenTUI markdown renderer, spine-mapper, turn-lifecycle.

## Full Code Path Audit

### Issue 1: Code blocks render with broken `│` separators

The user showed code rendering like:
```
│  │ //! PS5 Emulator Core — platform-independent engine components.
│        │ //!
```

This looks like the code block has extra left-padding or a border that creates visual `│` chars. The `│` is likely from the **spine rail** (the `SpineRail` component adds a vertical glyph at each line) or from **line number rendering** inside code blocks.

**Probable cause**: The `SpineProse` component renders markdown with code fences. OpenTUI's `MarkdownRenderable` might add line numbers or gutter indicators that create the `│` effect. Or the spine entry's left rail border bleeds into code blocks.

### Issue 2: Structured tool outputs render as raw XML

The user showed `<active-goal>...</active-goal>` rendered as plain text in the chat. This is tool output that contains XML. The `GenericTool` component renders tool output as text without parsing or syntax highlighting. XML/JSON in tool output should be formatted — at minimum, syntax-colored, and ideally collapsed by default with expand.

**Probable cause**: `GenericTool` renders `limited()` as plain text. No XML/JSON detection exists in the tool output renderer. We've already added table/KV/todo detection but not XML.

### Issue 3: "Working" never transitions to idle

The `runState` at `command-spine-shell.tsx:130` is:
```typescript
const runState = createMemo(() => (
  gateEntries().length ? "stop" : props.pending() ? "working" : "idle"
))
```

`props.pending()` comes from `messageMeta` memo at `session/index.tsx:304-316`:
```typescript
let pending: string | undefined
for (let i = list.length - 1; i >= 0; i--) {
  const message = list[i]
  if (message.role !== "assistant") continue
  if (!message.time.completed) {
    pending = message.id
    break
  }
}
```

The `pending` stays set until ALL assistant messages have `time.completed`. But what if there's an **orphaned assistant message** — a message that was created but never got a `time.completed`? This could happen if:
- The engine crashed mid-turn
- A streaming session was interrupted
- An older session has an incomplete message from a previous run

The reverse-scan finds the MOST RECENT assistant without `completed`. If this message is from a stale/crashed turn, it will never get `time.completed`, and `pending` stays stale forever.

**Additionally**: The `sessionStatusType` check at `turn-lifecycle.ts:55`: `if (!L.sessionTurnActive) return false`. If the session status is not active, streaming should stop. But `runState` in command-spine-shell doesn't check `sessionTurnActive` — it only checks `props.pending()`.

**Key insight**: `runState` depends SOLELY on `message.time.completed`. It doesn't account for session status (idle, finished, crashed). If the session is finished but the last message hasn't been explicitly marked completed, the "Working" state persists forever.

## Regression Analysis

**REG-1: Adding session status check to `runState` may cause flicker.** If the session status toggles rapidly during streaming, `runState` would flicker between "working" and "idle". **Fix:** Add session status as an OR condition — only go idle when BOTH `pending` is resolved AND session is not active. Addressed in plan.

**REG-2: Code block rendering fix may conflict with existing markdown renderer.** OpenTUI's `MarkdownRenderable` may have its own mechanisms. **Scope:** This is an upstream OpenTUI issue. We can mitigate by adjusting the `SpineProse` styling but cannot fix the markdown renderer itself. **Mitigation:** Reduce left padding on code blocks to minimize the `│` visual noise. Addressed in plan.

**REG-3: XML detection in GenericTool may conflict with existing format detection.** The `formattedOutput` memo already detects todos, tables, and KV. Adding XML detection adds a 4th case. Order matters — XML should be checked BEFORE KV (XML is an object-like string but should be treated as code). **Fix:** Add XML detection as the FIRST check (before todos/table/KV). Addressed in plan.

**REG-4: `sessionStatusType` may not be available in the `runState` computation.** `runState` is in `command-spine-shell.tsx` which receives `ShellProps`. Let me check if session status is available... `ShellProps` has `sessionStatus: () => sync.data.session_status[route.sessionID]`. This is available via `props.sessionStatus`. **Fix:** Use `props.sessionStatus()` in the `runState` memo.

## Bite-Sized Tasks

### Task 1: Fix "Working" never transitions to idle (3 min)

**Objective:** Add session status check to `runState` so it transitions to idle even if `message.time.completed` is stuck on a stale message.

**File:** `packages/tui/src/shell/command-spine/command-spine-shell.tsx` — line 130

**Current:**
```typescript
  const runState = createMemo(() => (gateEntries().length ? "stop" : props.pending() ? "working" : "idle"))
```

**Replace with:**
```typescript
  const runState = createMemo(() => {
    if (gateEntries().length) return "stop"
    // Only show "working" when both pending AND session is active.
    // Stale messages without time.completed shouldn't block idle transition.
    const sessionStatus = props.sessionStatus?.()
    const statusType = sessionStatus?.type
    const sessionActive = !statusType || statusType === "running" || statusType === "thinking"
    if (props.pending() && sessionActive) return "working"
    return "idle"
  })
```

**Verification:** After agent finishes a turn and the session goes idle, "Working" stops even if a stale message lacks `time.completed`.

3. **Code block fix is limited.** The `│` visual may be from OpenTUI's markdown renderer which we can't modify. If Task 3 doesn't fix it, this becomes a feature request for OpenTUI. **Risk acknowledged.**
